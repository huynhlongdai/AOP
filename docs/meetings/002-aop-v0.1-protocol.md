# Founding Company Meeting #002 — AOP v0.1 Protocol

Date: 2026-08-25

## Purpose

Define the first executable organizational protocol for AI companies. The meeting deliberately excluded marketplace/business discussion and focused on the minimum primitives, state machines, invariants, and interoperability boundaries required for implementation.

## Protocol position

AOP does not replace A2A or MCP.

```text
AOP: organization / role / authority / goal / work / decision / review
A2A: remote agent communication/interoperability
MCP: agent-to-tool/data interoperability
```

AOP is the organizational-semantics layer above transport and tool protocols.

## AOP v0.1 primitives

The initial protocol contains twelve core primitives:

1. Organization
2. Agent
3. Role
4. Goal
5. Task
6. Artifact
7. Decision
8. Event
9. Message
10. Lease
11. Permission
12. Review

Budget, Meeting, Team, Department, Contract, Reputation, and Marketplace are deferred from the interoperable core until later versions.

## Organization

Persistent root entity representing a company/team/organization.

Key properties:

- id
- name
- type
- mission
- owner
- root goal
- governance mode
- policies
- status
- revision/version

Critical invariant:

> Organization identity and state survive individual runtime processes.

## Agent

Agent represents a durable worker identity, not an execution process.

Key properties:

- identity/version
- capabilities
- runtime policy
- A2A/MCP interfaces
- organization membership
- role
- manager
- memory policy
- employment status

Runtime processes are separate and disposable.

## Role

Agent and Role are intentionally separate.

Role defines organizational purpose, reporting relationship, responsibilities, authority, and prohibitions. The same worker may hold different roles over time.

Roles form an Authority Graph used by Policy Engine decisions.

## Goal

Goal answers why work exists.

Key properties:

- organization
- objective
- owner
- parent goal
- success criteria
- priority
- status

Goals form a hierarchy and tasks must ultimately trace back to organizational objectives.

## Task / WorkTask

Task is the central work-contract primitive.

Required concepts:

- objective
- organization/goal
- created_by
- owner
- reviewer
- scope includes/excludes
- inputs and explicit artifact versions
- dependencies
- deliverables
- acceptance criteria
- constraints
- budget/limits
- state
- revision

### Task state machine

```text
PROPOSED
   |
 validate
   v
 READY <-------------------------------+
   |                                   |
 acquire lease                         | lease expiry/rework
   v                                   |
 LEASED                                |
   |                                   |
 start                                 |
   v                                   |
 RUNNING ------> BLOCKED --------------+
   |
 submit
   v
 REVIEW
  /   \
REWORK APPROVED
  |      |
 READY   v
      COMPLETED
```

Terminal states include COMPLETED, CANCELED, FAILED, and REJECTED.

A worker cannot directly declare a task COMPLETED. It submits work to REVIEW. Acceptance validation/review determines completion.

## Lease

Lease is a first-class execution-ownership mechanism.

Fields include:

- lease id
- task id
- agent id
- acquired/expires times
- heartbeat interval
- execution token
- attempt

When heartbeat stops and lease expires, the run is considered lost and the task can return to READY for another execution attempt.

## Artifact

Artifact is the primary durable work-output/handoff object.

Examples:

- PRD
- architecture
- API spec
- DB schema
- code commit
- test report

Artifact versions are immutable. A new change creates a new version and may supersede an older one.

The system tracks artifact consumers so that a new authoritative version can generate INPUT_STALE signals and trigger impact analysis.

## Impact analysis

An artifact update does not automatically restart every consumer task.

Change classification:

- trivial -> continue
- moderate -> review/recompile context
- breaking -> pause/rebase/replan

Graph dependencies identify candidates; deterministic rules and/or LLM analysis determine significance.

## Decision

Decision is authoritative organizational choice, separate from conversation.

Lifecycle:

```text
PROPOSED
   |
DISCUSSION
   |
APPROVAL_PENDING
  /             \
REJECTED        ACTIVE
                  |
               SUPERSEDED
```

Decisions record question, proposals, selected option, rationale, authority, scope, effective time, and affected artifacts.

Authority to approve is determined by role and policy, not self-declared by the reasoning agent.

## Permission

Permissions use bounded capabilities rather than unrestricted credentials.

Examples:

- repository.read
- branch.create
- commit.write
- pull_request.create
- production.deploy

Policies can deny capabilities, apply conditions, or require approval.

## Review

Review is structured organizational state, not only commentary.

Fields include:

- subject task/artifact
- reviewer
- review policy
- criteria
- evidence
- findings
- result

Lifecycle:

```text
PENDING -> IN_REVIEW -> PASS | REWORK | FAIL
```

## Message

Messages are used for:

- questions
- clarification
- notifications
- discussion
- negotiation

Messages are not authoritative for final decisions, specifications, task completion, or permissions.

A conversational agreement must be committed into a Decision/Artifact/Task mutation before it changes organizational truth.

Analogy:

> conversation = working tree; decision/artifact = organizational commit.

## Event

Event is an immutable fact about a committed state transition.

Fields include:

- event id
- organization
- organization sequence
- type
- actor
- entity/aggregate
- from/to state when relevant
- causation id
- correlation id
- timestamp

Organization sequence is required because timestamps alone are insufficient for deterministic historical ordering.

## Initial event catalog

- ORGANIZATION_CREATED
- AGENT_JOINED / ACTIVATED / SUSPENDED / LEFT
- ROLE_ASSIGNED / ROLE_CHANGED
- GOAL_CREATED / UPDATED / COMPLETED
- TASK_CREATED / READY / LEASED / STARTED / BLOCKED / SUBMITTED_FOR_REVIEW / REWORK_REQUESTED / COMPLETED / FAILED / CANCELED
- LEASE_ACQUIRED / HEARTBEAT / EXPIRED
- ARTIFACT_CREATED / VERSION_CREATED / APPROVED / SUPERSEDED
- DECISION_PROPOSED / APPROVED / REJECTED / SUPERSEDED
- REVIEW_STARTED / PASSED / FAILED
- PERMISSION_GRANTED / REVOKED
- HUMAN_APPROVAL_REQUIRED / RECEIVED

## State storage

PostgreSQL is the initial authoritative store.

Initial relational model includes:

- organizations
- agents
- organization_agents / role assignments
- roles
- goals
- tasks
- task_dependencies
- task inputs/outputs
- artifacts / artifact_versions
- decisions
- reviews
- leases
- permissions
- events

Graph views are derived from relational edges initially; no graph database is required for MVP.

Derived/auxiliary stores:

- object storage for artifact contents
- Git for code
- vector/search for derived memory
- Redis only where useful for ephemeral cache/locks
- event stream/outbox for asynchronous processing

## Outbox pattern

Authoritative mutation, event creation, and outbox insertion should commit in the same PostgreSQL transaction. Asynchronous publishers can safely retry without risking “DB changed but event disappeared.”

## Context Compiler v0.1

`compile_context(agent_id, task_id)` collects:

1. agent identity
2. current role
3. role policies
4. organization mission
5. current goal
6. task contract
7. dependencies
8. required artifact versions
9. active decisions
10. prior attempts
11. relevant memory
12. tool permissions
13. output schema

Authoritative mandatory context is not subject to semantic-ranking eviction.

## Scheduler

Initial scheduler is deterministic:

1. observe READY task
2. verify dependencies
3. verify required artifacts
4. identify eligible capabilities
5. filter permissions/availability
6. rank candidates
7. create task run/lease

LLMs may later help ranking, but state/lease transitions stay deterministic.

## Capability-gap and HR flow

An agent may reject a task with structured reason such as capability_gap. If no eligible worker exists, the organization generates a workforce-gap event. A future HR agent can search the marketplace, trial candidates, and recommend hiring under bounded authority.

## Runtime contract

Minimum runtime interface:

- initialize/start
- execute
- pause
- resume
- cancel
- heartbeat
- report
- shutdown

Agents emit structured commands/actions. They never directly mutate authoritative database state.

## Command -> Policy -> Event

Central execution pattern:

```text
Agent
  |
command
  v
Organization Kernel
  |
Policy Engine
 /         \
DENY      ALLOW
           |
      transaction
           |
          event
```

## Command catalog v0.1

- organization.read
- goal.create / update
- task.create / claim / start / block / submit_review / cancel
- artifact.create / revise
- decision.propose / approve / reject
- review.start / submit
- message.send
- permission.request
- agent.delegate
- lease.heartbeat

No agent receives direct SQL mutation access.

## Adapter architecture

The runtime interface is provider-neutral. Adapters may include:

- OpenAI
- Claude
- Gemini
- local model/runtime
- OpenClaw
- remote A2A agent
- custom HTTP runtime

MCP is used for tool capabilities. A2A is used for remote-agent interoperability. AOP remains the organizational-control layer.

## Protocol invariants v0.1

1. Agent cannot mutate authoritative state directly.
2. All authoritative mutations go through Kernel Commands.
3. Every accepted authoritative mutation emits an Event.
4. Messages are not authoritative state.
5. Artifact versions are immutable.
6. Task completion requires acceptance validation.
7. Only one active execution lease is allowed per task/run ownership policy.
8. Authority is determined by Role + Policy, not agent reasoning.
9. Agent runtime may disappear without destroying organization state.
10. Context is compiled from authoritative state, not reconstructed from conversation alone.
11. Every task traces to an objective/goal.
12. Every organizational action identifies an actor.
13. External effects require explicit capability.
14. Changed authoritative inputs trigger dependency-impact evaluation.
15. Agents may propose authority changes but cannot grant themselves authority.

## PoC and chaos tests

The five-worker Software Company remains the target. It must be tested against:

- runtime crash
- lease expiry
- changed API specification
- conflicting assumptions
- agent claiming done while tests fail
- unauthorized production action
- excessive workforce creation/budget violation
- founder requirement change mid-execution

The meeting concluded that AOP v0.1 is sufficiently defined to move into implementation architecture.
